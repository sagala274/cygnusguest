--------------------------------------------------------------------
GAMBARAN UMUM SISTEM
--------------------------------------------------------------------

PUSSIBERAL Guest Management adalah aplikasi web untuk mengelola
pendaftaran tamu di sebuah fasilitas dengan kebutuhan keamanan
(security clearance tamu, kategori risiko, dsb). Tiga peran pengguna:

  - Administrator : akses penuh ke semua fitur
  - Verifikator   : menyetujui/menolak pendaftaran, lihat laporan
  - Pos Depan     : mendaftarkan tamu, check-in/check-out

Stack teknologi:
  - Frontend : HTML/CSS/JavaScript murni (tanpa framework), multi-page
  - Backend  : Node.js 20 + Express 4 (REST API)
  - Database : MySQL 8.0
  - Deploy   : Docker Compose (3 container: mysql, backend, frontend)
               di satu server Ubuntu, di belakang Nginx sebagai
               reverse proxy + terminasi TLS

Alasan stack ini dipilih: sederhana, tidak butuh build tooling
kompleks (tidak ada React/Vue/bundler), mudah di-maintain oleh tim
yang mungkin tidak selalu punya latar belakang frontend modern, dan
cukup untuk kebutuhan aplikasi internal skala kecil-menengah.

Pihak eksternal melakukan scan (Pentest-Tools.com, Light scan, 40
test) terhadap server. Hasil laporan itu diberikan, lalu diminta
dianalisa dan diperbaiki. Hasil awal: 0 Critical, 0 High, 1 Medium,
5 Low, 1 Info. Perbaikan yang dilakukan:

  - Header keamanan HTTP ditambahkan di Nginx: Content-Security-
    Policy (ketat, script-src hanya 'self' -- tidak ada inline
    script sama sekali di seluruh aplikasi), Strict-Transport-
    Security, X-Content-Type-Options, Referrer-Policy.
  - `server_tokens off` -- versi Nginx tidak lagi terekspos di
    header respons.
  - Bug XSS ditemukan lewat audit kode mandiri (bukan dari laporan
    scanner-nya sendiri): fungsi escapeHtml() versi awal memakai
    trik textContent->innerHTML yang TIDAK meng-escape tanda kutip,
    jadi tidak aman dipakai di dalam atribut HTML (mis.
    data-username="..."). Diperbaiki jadi escape manual yang aman
    di semua konteks.
  - Satu temuan (sertifikat SSL tidak dipercaya) sengaja dibiarkan
    terbuka karena akar masalahnya butuh domain resmi terdaftar,
    yang belum tersedia untuk server ini.

Setelah semua perbaikan selesai, diminta dokumentasi teknis formal
-- inilah asal-usul `04_dokumentasi_teknis_dan_keamanan.md`, yang
kemudian jadi acuan gaya penulisan untuk seluruh dokumentasi
berikutnya (05 dan 06). Dokumentasi ini juga sempat dipublikasikan
sebagai halaman web (Artifact) selain berkas .md-nya.

Pelajaran penting: laporan vulnerability scanner otomatis (apalagi
"Light scan") tidak menguji semua kelas kerentanan secara mendalam.
Audit kode manual tetap diperlukan untuk area yang tidak tercakup,
seperti SQL Injection (di aplikasi ini dicegah lewat parameterized
query di semua query database, tanpa kecuali) dan XSS.

FASE 7 -- BUG KRITIKAL: SEMUA MENU HILANG
--------------------------------------------------------------------

PROMPT ASLI:
  "dimana menu chat AInya?"
  "deploy sekarang, jangan lupa config AInya."
  "perbaiki banyak eror, seluruh menu tidak muncul"

Setelah deploy pertama fitur AI Chat, SELURUH halaman kehilangan
styling dan menu sidebar kosong total -- bukan cuma menu baru, semua
menu lama pun ikut hilang.

Investigasi (bukan tebak-tebakan, langsung cek langsung ke server):
  1. Cek apakah file assets (app.js, style.css) bisa diakses -> semua
     mengembalikan HTTP 404.
  2. Cek isi container frontend -> ternyata direktori
     frontend/public/assets/ punya permission 700 (hanya bisa dibaca
     root), padahal proses Nginx di dalam container jalan sebagai
     user non-root.

Root cause: proses transfer file dari Windows ke server memakai
`scp -r`, dan itu membuat permission direktori yang salah (700,
bukan 755 yang seharusnya).

Perbaikan darurat: chmod manual di server, lalu build ulang TANPA
cache (build pertama sempat masih memakai layer lama yang membawa
permission salah).

Pelajaran penting: satu kesalahan kecil di lapisan infrastruktur
(permission file) bisa membuat SELURUH aplikasi terlihat rusak total,
padahal kode aplikasinya sendiri sama sekali tidak bermasalah. Ini
juga jadi alasan kuat kenapa Fase 8 (migrasi ke git) penting -- bukan
cuma soal kerapian, tapi menghilangkan seluruh kelas bug ini secara
permanen.

FASE 8 -- MIGRASI DEPLOYMENT: SCP MANUAL -> GIT PULL
--------------------------------------------------------------------

PROMPT ASLI:
  "commit dan push lalu fixkan di server"
  "https://github.com/sagala274/cygnusguest.git"
  "lanjutkan, ssh key sudah saya masukkan"

Setelah insiden Fase 7, alur deploy diubah total.

Temuan menarik saat proses ini: ternyata SUDAH ADA repository git
sebelumnya (tersembunyi, satu level di atas folder aplikasi),
terhubung ke GitHub (github.com/sagala274/cygnusguest), berisi 2
commit riwayat dari pembangunan awal aplikasi -- dibuat sendiri oleh
pengguna lewat GitHub sejak awal proyek (terlihat dari riwayat
prompt paling awal yang berisi perintah `git init` bawaan GitHub).
Sempat keliru membuat repository BARU di tempat yang salah sebelum
menyadari ini -- lalu dibersihkan dan memakai repository asli yang
sudah ada.

Langkah migrasi:
  1. Kode di-commit dan di-push ke GitHub (autentikasi lewat SSH key
     yang didaftarkan pengguna sendiri di GitHub).
  2. Server: clone repository ke lokasi baru, lalu direktori aplikasi
     lama (/opt/pussiberal) diubah jadi SYMLINK yang menunjuk ke hasil
     clone -- supaya semua path lama (docker-compose.yml, volume
     backup, dst) tetap bekerja tanpa perlu diubah satu-satu.
  3. Data runtime yang TIDAK boleh ikut ke git (.env berisi password
     database, backups/ berisi data pribadi tamu asli, certs/ berisi
     kunci privat TLS) dipindahkan dengan hati-hati ke lokasi baru,
     dan tetap dijaga lewat .gitignore supaya tidak pernah ter-commit.
  4. Direktori lama disimpan sebagai cadangan (.pre-git-bak), tidak
     langsung dihapus, sebagai jaring pengaman.

Alur deploy baru, jauh lebih sederhana dan tidak lagi rawan bug
permission:

    # Di komputer lokal:
    git add -A && git commit -m "..." && git push origin main

    # Di server:
    cd /opt/cygnusguest && git pull
    cd pussiberal-app && docker compose build && docker compose up -d

Pelajaran penting: `git clone`/`git pull` TIDAK PERNAH membawa
permission aneh seperti yang terjadi dengan `scp` dari Windows --
migrasi ini bukan cuma memperbaiki gejala, tapi menghilangkan akar
masalahnya secara permanen untuk semua deploy ke depannya.

FASE 9 -- MIGRASI AI CHAT: ANTHROPIC LANGSUNG -> OPENROUTER
--------------------------------------------------------------------

PROMPT ASLI:
  "untuk konfigurasi AI, jangan hanya berpatokan pada anthropic.
   Saya mau memakai segala jenis AI yg ada di openrouter."

Atas permintaan eksplisit, integrasi AI diubah total dari memanggil
Claude langsung, menjadi memakai OpenRouter -- sebuah gateway yang
meneruskan ke ratusan model dari berbagai vendor (Anthropic, OpenAI,
Google, Meta, dll) lewat satu API key, dengan format request yang
kompatibel dengan standar OpenAI.

Dampak teknis:
  - Dependency SDK Anthropic dihapus total, diganti pemanggilan
    `fetch` native Node.js langsung ke endpoint OpenRouter -- tidak
    ada dependency baru yang perlu ditambahkan.
  - Field "Model" di halaman Konfigurasi AI diubah dari daftar
    dropdown tetap (3 model Claude) menjadi kolom pencarian yang
    terhubung ke katalog LIVE OpenRouter -- admin bisa pilih model
    apa pun dari vendor mana pun.

FASE 14 -- BUG: CACHE BROWSER MENAHAN UPDATE
--------------------------------------------------------------------

PROMPT ASLI:
  "masih belum ada untuk telegram"

Setelah Fase 13 diperbaiki di server, pengguna MASIH melihat menu
lama saat membuka aplikasi di browser (disertai tangkapan layar).
Digali lebih dalam:

Root cause yang lebih dalam: Nginx tidak pernah mengirim header
`Cache-Control` untuk file HTML/JS/CSS. Tanpa header ini, browser
modern melakukan "heuristic caching" -- boleh menyimpan file lama
tanpa aturan jelas kapan harus dianggap kedaluwarsa. Ini artinya
masalah "fitur baru tidak muncul" ini BERPOTENSI TERULANG di SETIAP
deploy berikutnya, bukan cuma sekali ini saja.

Perbaikan: tambah `Cache-Control: no-cache` -- ini tetap mengizinkan
browser menyimpan cache (efisien), tapi MEWAJIBKAN validasi ulang ke
server di setiap request, sehingga versi terbaru selalu terdeteksi
otomatis tanpa perlu hard-refresh manual.

Satu bug tambahan sempat diperkenalkan SENDIRI di tengah proses
perbaikan ini: percobaan pertama menaruh header Cache-Control di
dalam sebuah blok `location` khusus di konfigurasi Nginx -- ternyata
ini justru MENGHAPUS seluruh header keamanan (hasil hardening di
Fase 5) untuk request yang cocok dengan lokasi tersebut. Penyebabnya
perilaku Nginx yang tidak intuitif: `add_header` di dalam sebuah
`location` TIDAK mewarisi daftar `add_header` dari blok `server`
induknya, melainkan MENGGANTIKANNYA total. Ditemukan lewat verifikasi
langsung (`curl -I` mengecek header apa saja yang benar-benar
dikirim), lalu diperbaiki dengan memindahkan header Cache-Control ke
level `server`, sejajar dengan header keamanan lain.

Ada juga pertanyaan lepas terkait fitur ini yang dijawab langsung
tanpa perlu perubahan kode:
  "cara akses mendapatkan chat id di telegram"

Pelajaran penting dari Fase 13-14: SETIAP KALI selesai deploy,
verifikasi LANGSUNG ke server (bukan cuma percaya command berhasil
tanpa error) -- cek file benar-benar ter-update, cek header respons
benar-benar sesuai harapan. Asumsi adalah sumber bug paling umum
dalam proses deployment.

FASE 20 -- HARDENING KEAMANAN: UPLOAD FOTO & SESI LOGIN
--------------------------------------------------------------------

PROMPT ASLI:
  "laksanakan sanitasi terhadap file upload terutama pada bagian
   foto. Jangan sampai bisa membaca file .php.jpg sehingga
   kemungkinan bisa diupload malware"
  "ini ada vulnerability akses, yaitu ketika saya close tab pada
   browser atau close browser. Saya langsung mendapatkan akses masuk

   langsung dapat akses masuk ke akun yg dimasuki sebelumnya"

Dua permintaan keamanan terpisah, ditangani dengan pendekatan yang
sama: AUDIT dulu secara menyeluruh sebelum memperbaiki apa pun.

Untuk permintaan pertama, audit read-only (lewat subagent riset
terpisah supaya cakupannya tuntas) atas seluruh jalur yang
bersinggungan dengan file/gambar menyimpulkan: aplikasi ini TIDAK
PERNAH menyimpan foto sebagai file di server -- semua foto (tamu,
KTP) disimpan sebagai data URL base64 langsung di database. Skema
serangan "upload file .php.jpg lalu server menjalankannya" TIDAK
BERLAKU secara arsitektur di aplikasi ini. Meski begitu, dua celah
nyata tetap diperbaiki sebagai defense-in-depth: validator foto
diperkeras (regex diikat penuh + verifikasi *magic bytes* asli
PNG/JPEG/WebP, bukan cuma percaya prefix teks), dan satu titik render
`<img src>` yang tidak di-*escape* (celah berbentuk stored-XSS,
sebelumnya diredam CSP ketat tapi tetap diperbaiki). Perbaikan
diuji langsung dengan payload PHP yang disamarkan sebagai PNG,
prefix rusak, dan sisipan `<script>` setelah data gambar valid --
semuanya berhasil ditolak, gambar asli tetap diterima.

Untuk permintaan kedua: akar masalahnya token JWT disimpan di
`localStorage` (bertahan permanen sampai dihapus manual), bukan
`sessionStorage` (otomatis kosong saat tab/browser ditutup).
Diperbaiki dengan memindahkan seluruh fungsi sesi ke `sessionStorage`
-- efeknya, siapa pun yang sedang login di mana pun otomatis diminta
login ulang begitu perbaikan ini di-deploy.

Pelajaran penting: laporan "kerentanan" dari pengguna (upload
malware) tidak selalu berarti kerentanan itu benar-benar ada di
arsitektur yang dipakai -- yang penting adalah MEMBUKTIKANNYA lewat
audit nyata (bukan asumsi ke arah mana pun), lalu tetap memperkuat
lapisan pertahanan yang genuinely lemah begitu ditemukan, walau
bukan jalur serangan yang awalnya dikhawatirkan.

     disimpulkan, baru diperbaiki: kartu "Total Tamu" diganti

RINGKASAN POLA & PELAJARAN LINTAS-FASE
====================================================================

Beberapa pola yang berulang dan layak diingat baik-baik:

1. BUG INFRASTRUKTUR SERING TERLIHAT SEPERTI BUG APLIKASI.
   Tiga insiden besar (menu backup hilang di Fase 4, semua menu
   hilang di Fase 7, dan menu Telegram tidak muncul di Fase 13-14)
   SAMA SEKALI bukan masalah di kode aplikasi -- soal permission
   file, lupa rebuild image Docker yang tepat, dan cache HTTP. Kalau
   panik dan langsung mengubah-ubah kode aplikasi tanpa investigasi
   yang benar, bug seperti ini bisa sangat membuang waktu.

2. SELALU VERIFIKASI LANGSUNG KE SUMBERNYA, JANGAN BERASUMSI.
   Setiap dugaan root cause di dokumen ini dikonfirmasi lewat
   pengecekan langsung (curl ke server, baca isi container, cek
   struktur tabel database) -- bukan tebakan. Ini yang membuat
   perbaikan tepat sasaran, bukan coba-coba.

3. KEAMANAN DAN KENYAMANAN SERING TARIK-MENARIK, DAN KEDUANYA PENTING.
   Header Cache-Control yang baik untuk kenyamanan (update cepat
   terlihat) sempat tanpa sengaja menghapus header keamanan yang
   sudah susah payah diperbaiki di fase sebelumnya. Perbaikan yang
   benar bukan memilih salah satu, tapi memastikan keduanya berjalan
   bersamaan dengan struktur konfigurasi yang benar.

4. LAYANAN EKSTERNAL (API PIHAK KETIGA) PERLU DIUJI NYATA, BUKAN
   DIASUMSIKAN. Baik soal model AI gratis (Fase 10) maupun batasan
   API Claude yang berubah dari waktu ke waktu (Fase 6) -- keduanya
   menunjukkan pentingnya verifikasi langsung ke dokumentasi/perilaku
   terkini, bukan mengandalkan asumsi lama.

5. SETIAP FITUR SENSITIF (API KEY, PASSWORD) SELALU DIENKRIPSI DI
   DATABASE, TIDAK PERNAH DIKEMBALIKAN APA ADANYA LEWAT API. Pola
   ini konsisten dipakai untuk API key AI (Fase 6) maupun bot token
   Telegram (Fase 12) -- kunci enkripsi diturunkan dari secret yang
   sudah ada, supaya tidak menambah kompleksitas konfigurasi.

6. PROSES YANG ITERATIF ITU NORMAL, BUKAN TANDA PERENCANAAN YANG
   BURUK. Fase 3 dan Fase 12 menunjukkan pola yang sama: permintaan
   awal disempurnakan lewat beberapa prompt susulan begitu hasilnya
   terlihat nyata. Requirement yang sepenuhnya sempurna sejak
   prompt pertama jarang terjadi -- yang penting desainnya cukup
   fleksibel untuk menampung revisi tanpa bongkar total.

7. KOMPUTER PENGEMBANGAN LOKAL BELUM TENTU SERVER PRODUKSI --
   VERIFIKASI TOPOLOGI DEPLOY SEBELUM MENGASUMSIKANNYA. Insiden di
   Fase 18 (Docker lokal gagal jalan, sempat memasang WSL dan
   me-restart komputer sebelum sadar server sungguhan ada di tempat
   lain) menunjukkan pentingnya mengecek dokumentasi deploy yang
   sudah ada lebih dulu, sebelum mencoba menjalankan sesuatu secara
   lokal dan menganggap itu jalan pintas yang lebih cepat.

8. SEBELUM MEMPERBAIKI SESUATU YANG "TERLIHAT SALAH", BUKTIKAN DULU
   DENGAN DATA NYATA. Laporan "Total Tamu = 9 tapi statistik
   perangkat = 10" di Fase 22 ternyata bukan bug -- dua angka itu
   memang mengukur hal berbeda (pendaftaran vs individu). Query
   langsung ke database membuktikan itu SEBELUM menyimpulkan atau
   mengubah kode apa pun -- pola yang sama dengan Pelajaran #2, tapi
   khusus untuk kasus "angka yang terlihat tidak sinkron" yang mudah
   disalahsangka sebagai kesalahan hitung.
